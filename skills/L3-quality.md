## 假设验证：量化先于实现

- **拍脑袋的阈值 / 评分 / 相关性假设，写实现前先建离线 eval 出 before/after**：一批真样本 + 人工标注 + P/R/F1 表，把"这个方向有没有用"从争论变成测量。20 行脚本能在写第一行实现前砍掉一个会白做的功能——比"实现一版→上线→观察几周→才发现没用"省一个数量级。
- **看似"调参"的问题，可能是机制的结构上限**：调阈值前先问"这个机制理论上分得开吗"。例：substring 评分分不开「OpenAI 做产业」vs「OpenAI 做医疗」（同含实体词），跨语言关键词对源也命不中——是结构分不开，调参数白费。数据能把"参数没调好"和"机制到顶"区分开；到顶了就换机制（如语义判断）或如实记为已知天花板，别在参数上耗。
- 经验来源：`docs/practice-log.md` 2026-06-23（ADR-0010 (1c) 沾边离题阈值：离线 eval 证伪 lexical，最优变体 +2.5pp F1 封顶）；可复跑基线见 `evals/relevance-floor-eval.mjs`。

## 验证的保真度：证明你**真的**验证了

比"有没有验证"更要问"验证走的是不是与生产一致的路径"。不等价的验证比不验证更危险——它发的是假通行证。

- **模拟 / probe 必须走与生产一致的代码路径，否则是假绿**：用便捷替身（`matchAll` 正则近似 `fast-xml-parser`、`curl` 近似 `fetchRss`）验证 = 假通行证——替身"自然丢弃坏输入"而生产代码"抛错"，结论方向性错误。要么调真函数，要么先证替身在关键行为上等价；宁可如实说"没验证"，也别拿不等价模拟当"已验证"。**review 的头号价值是复现"你说你验证过的那步"，不只是读 diff。**
- **验证脚本自身先被怀疑——尤其当它跑出反常数字时**：反常测量先假设是测量错、逐条 dump 真实例核对，别直接采信（一个错的高误匹配率会"论证"出一个有害的修法）。注意**归一化顺序制造的假信号**：先剥空白 / fold 再判边界或子串，会把原本分开的 token 粘连出原文不存在的冲突——判"相邻 / 边界"关系要在保留原始分隔的文本上判。
- **诊断落到"读几条真实数据行"，别停在聚合指标**：比率（blocked 12% / multi_source 1.5%）会把人引向错的缺口或错的归因；拉几条真实洞察 / 行读下来，才分得开"缺陷 vs 内容结构 vs 校验粒度误拦"。
- **备忘 / 文档里的数字会过期，决策依赖它前回到代码 + 生产数据真跑一次**：边际价值常不是"确认结论"而是"发现结论方向错了"（如 shipped 789→实测 696、"纯展示"→实际喂补引）。改一个看似糙的实现前，先在真实数据上量"改完更准还是更差"，别默认现状是 bug。
- **接入 / 审计外部源，先复现生产抓取全路径（robots + WAF/IP 段 + 大小上限），只验"可达 200/N 条"必漏判**（已三次实锤：robots→WAF→8MB cap）。本地 curl/probe 直连会绕过这三关。
- 经验来源：`docs/practice-log.md` 2026-06-19 / 06-26 / 06-30（PZ 假绿）/ 07-01（重测反转搁置结论）；memory `oversized-feed-8mb-cap` / `verify-commit-object-not-worktree`。
