# 三个栏目的关系分析

> 范围：基于 `src/lib/config/defaults.yaml`、分类/选材/报告/图谱实现以及 ADR-0010、ADR-0012 的已落地状态进行的静态分析；不读取或写入 live SQLite。
>
> 结论先行：三个栏目不是父子栏目，也不应合并成一个大栏目。它们构成「上游变化 → 工程采用 → 风险与控制」的研究组合，但系统当前把它们实现成**内容与历史状态均隔离的三个主题**。这能保证每栏信噪比与可溯源性，却使跨栏目关联只能靠读者在报告库中自行发现。

## 1. 当前栏目模型

| 栏目（Topic） | 分类（facets） | 行为策略（archetype） | 默认源（启用 / 总数） | 研究角色 |
|---|---|---:|---:|---|
| AI 时代的软件工程 `t_code_agents` | `domain:software-engineering` + `lens:technical` | `deep_vertical` | 16 / 17 | 把 AI 能力转化为研发流程、编码 Agent、工具和评测实践 |
| AI 时代的安全 `t_prompt_injection` | `domain:security` + `lens:technical` | `deep_vertical` | 11 / 15 | 观察 AI 系统、模型和 Agent 的攻击面、攻防与治理控制 |
| AI 产业动态 `t_ai_industry` | `domain:foundation-models` + `lens:business` | `horizontal_pulse` | 5 / 5 | 观察模型厂商、资本、算力、政策和产品发布等外部驱动 |

这里有三个互不替代的轴，不能再混为“栏目关系”。

- `topic_id` 是功能与状态边界：决定内容进入哪一次分析、历史事件池和报告链。
- `facets` 是浏览与筛选边界：`domain` 回答“研究对象是什么”，`lens` 回答“以技术还是产业眼光看”。因此“产业”不是软件工程、安全的父类，而是基础模型相关内容的 `business` 视角。
- `archetype` 是选材策略，不是内容分类。两个技术垂直主题采用软相关策略以保护研究型弱关键词内容；产业动态采用关键词硬下限以避免泛厂商 PR 把分析池淹没。

## 2. 业务上的关系：一个三角，而不是一条目录树

```
基础模型、厂商竞争、算力、资本、监管
              │
              │ 外部驱动 / 约束
              ▼
AI 产业动态 ─────→ AI 时代的软件工程
      │                 │
      │ 供应链、模型能力 │ Agent、代码、工具链改变攻击面
      │                 ▼
      └────────────→ AI 时代的安全
             风险、合规、控制反向约束工程采用
```

推荐将关系理解为三类，而非给栏目强行排序：

1. **产业 → 工程：能力与供给关系。** 模型/API 发布、价格和算力供给会改变编码 Agent 的可行边界、成本和工具选型。
2. **工程 ↔ 安全：应用—控制的双向关系。** 更自主的代码/Agent 工作流带来权限、提示注入、供应链和数据泄漏风险；安全要求又会反过来约束工程的评测、隔离、审计与发布流程。
3. **产业 → 安全：外部风险与治理关系。** 厂商策略、模型能力跃迁、政策与资本投入会改变攻击能力、模型供应链和合规约束。它通常是安全栏目的一段背景，不等价于安全证据本身。

由此可知：产业动态是**共享的上游上下文**，不是“总览版软件工程 + 安全”；软件工程与安全是**并列的下游技术栏目**，并且在 Agent、模型供应链、可信性和治理处有高价值交集。

## 3. 系统中的真实关系与隔离边界

### 3.1 路由：默认配置完全隔离，但模型允许共享

默认 37 个源中，没有一个 `Source.topic_ids` 同时配置多个栏目。采集后，`ContentItem.topic_ids` 直接继承源配置；`selectAnalysisItems` 只按一个 `topic_id` 取候选。因此，默认数据面是三块互斥的池子：

```
16 个启用源 ─→ t_code_agents      ─→ 独立分析 / 校验 / 报告
11 个启用源 ─→ t_prompt_injection ─→ 独立分析 / 校验 / 报告
 5 个启用源 ─→ t_ai_industry      ─→ 独立分析 / 校验 / 报告
```

数据模型支持把一个源挂到多个主题；同一 `ContentItem` 可因此获得多个 `topic_ids`，而设置页也能表达这一配置。但这只是**重复路由能力**，不是跨栏目关系能力：它会让同一内容分别进入两次独立分析，而不会产生“该内容如何影响另一栏目”的判断。

这项隔离是有意的。生产复盘已经确认：同事件的多源覆盖常常发生在不同主题，当前架构按设计将其分开；若为了提高单主题的多源率而强行合并，会制造弱连接而非更强的洞察。

### 3.2 状态：跨期演化也被 topic 隔离

`event_id` 的历史池只在同一 `topic_id` 内参与“是否同事件 / 是否续报”判断。报告前后链同样只连接同主题的 daily 链或深挖链。结果是：

- 同一厂商发布在产业动态与软件工程中分别被报道时，不会被识别为同一跨栏事件；
- 安全栏目跟进某个工程实践时，不会自动回链到相关的软件工程报告；
- 这避免了不同研究问题被错误去重，但也没有留下“同一事件的不同视角”这一层资产。

### 3.3 检索与图谱：可发现相关项，尚未建关系

报告库已可以按 `domain`、`lens`、`topic`、标签、实体和全文组合检索，因此读者能手工查找跨栏目共同实体（例如模型厂商、产品或标准）。但查询结果只是并列的报告集合。

实体共现图也按 `topic_id` 装配：边代表“同一条洞察中共同出现”，不是“跨栏目语义关系”。ADR-0012 已明确当前没有“发布 / 收购 / 依赖 / 对立”等有向关系抽取；生产测量也验证三栏的图密度差异很大，不能拿某一栏的图阈值或模式迁移到另一栏。

## 4. 当前设计的收益与缺口

| 维度 | 已获得的收益 | 代价 / 缺口 |
|---|---|---|
| 选材质量 | 不让泛产业源挤占工程或安全分析池；不同栏目可采用不同相关性策略 | 共同事件需在多个栏目重复分析 |
| 可溯源 | 每份报告、洞察和引用都有明确 topic 归属，避免跨域结论把背景当证据 | 无法直接回答“这条产业新闻对工程/安全分别意味着什么” |
| 历史演化 | 每栏的 event 去重、续报与报告链语义清晰 | 同事件的跨栏演化没有统一 ID 或导航 |
| 发现能力 | 全局报告库支持实体/全文/分面交叉检索 | 检索是“找得到”，不是“系统已判断两栏有关” |
| 图谱 | 单主题图规模可控、可回溯到洞察和引用 | 图不跨栏目，且只有无向共现，不能表达影响/风险/缓解 |

最重要的判断是：这不是“栏目割裂的 bug”，而是产品先保证主题内连续性与证据边界的合理取舍。真正缺的是一个**位于报告发布之后、不会反向污染主题内分析的关系层**。

## 5. 建议：先建“跨栏目事件导航”，不要先共享源或合并栏目

### P0：先量化需求，不改变生成链

对已发布报告建立只读诊断：按标准化实体、时间重叠、共有 `content_item_id` / URL 与相近事件描述，统计跨栏目候选对。输出应区分：

P0 的比较只能使用字段和值规则可解释的确定性信号（例如规范化实体、URL、时间窗与标准化事件锚点）；不调用 LLM、不写入关系记录，也不改变任何主题的采集、分析、去重或报告链。

- 强候选：同一原文或同一规范事件锚点；
- 中候选：核心实体重合且时间接近；
- 弱候选：仅有宽泛实体（如 OpenAI）重合，默认不展示。

验证指标应是“候选中人工确认有用的比例”和“用户从一个栏目跳到另一个栏目后的阅读/深挖行为”，而不是把跨栏目 `multi_source` 比率抬高。

### P1：确定性候选链接 + 人工确认

在报告详情页增加“相关栏目视角”区块，仅显示候选报告及其来源依据（共有实体、共同原文或时间窗口），标记为“关联候选”而不是事实结论。确认后写入一个独立的关系记录，例如：

```ts
CrossTopicLink {
  from_report_id: string
  to_report_id: string
  relation: "upstream_driver" | "engineering_impact" | "security_implication" | "shared_event"
  evidence: EntityRef[] // 只能引用已发布且通过校验的报告/洞察/引用
  status: "candidate" | "confirmed" | "dismissed"
  created_by: "deterministic" | "human"
}
```

这层应只消费已发布、可回溯的证据；不改变 `ContentItem.topic_ids`、主题内 `event_id`、引用白名单或报告生成。这样既不把“相关”误写成“因果”，也不削弱现有可信度红线。

### P2：有证据的类型化关系，最后才考虑 LLM

当 P1 证明关系导航真的被使用后，再引入“影响 / 暴露风险 / 缓解 / 竞争替代”等类型化关系。LLM 若参与，必须逐关系输出证据锚，并单独校验“关系陈述是否由该证据支持”；这会改 prompt/校验逻辑，必须先写 spec、跑 eval-gate，且不能拿实体共现当因果证明。

## 6. 不建议做的事

1. **不把 AI 产业动态改成两栏的父栏目。** 它的 `business` lens 与两栏的 `technical` lens 正交，语义会被误导。
2. **不为了“关联”把所有泛 AI 源挂给所有栏目。** 这会重新引入已被生产数据证实的噪声与候选池稀释。
3. **不复用 topic 内 `event_id` 作为全局事件 ID。** 其现有语义服务于单栏不复报；全局化会让不同研究问题被错误去重。
4. **不把实体共现图升级解释为跨栏目因果图。** 共现只能产生候选，不能证明影响、风险或缓解关系。

## 7. 推荐的产品表达

用户界面应保留三个平级栏目，并在每份报告中增加可验证的“相关视角”导航：

```
AI 产业动态：模型/API/资本发生了什么？
        ├─→ 软件工程：它如何改变研发与工具链？
        └─→ 安全：它带来什么攻击面、治理或控制要求？
软件工程 ⇄ 安全：工程实践与安全控制如何彼此约束？
```

这比“按领域再分一层目录”更符合当前数据结构，也让跨栏目价值建立在可回溯的证据与明确的关系类型之上。
