# Spec: Daily Brief 选择质量与空刊可解释性

> V1 · 状态：🟢 Implemented（待生产验收）· 2026-08-11

## 背景

Daily Brief 的分析选择会优先保留近期输入，但报告层在存在任何近期候选时，曾要求**每一条**发布洞察都引用近期候选。
这使引用了较早、但已通过 `pass/support` 校验且从未发布过的洞察被整体过滤；空刊页面也只展示原始计数，运营人员难以区分
“无输入 / 校验失败 / 新鲜度过滤 / 已发布去重”。

## 决定与边界

1. 发布引用白名单不变：仅 `verdict=pass` 且 `consistency=support` 的引用可进入报告。
2. 近期证据仍是 Brief 的主通道：有近期候选时，带近期成功校验证据的洞察按既有 14 天事件去重规则发布。
3. 增加最多两条 `补充发现`：仅限本轮分析得到、带 `event_id`、至少一条白名单引用、且该 event 在 14 天发布基线中从未出现的非近期洞察。
   它不能作为“今日新事件”表述，报告中必须显式标记 `〔补充发现〕`；没有 `event_id` 的较早趋势不得借此旁路发布。
4. 已发布 event 的较早证据不得因补充发现再次发布；近期证据的“新增成功校验证据”例外维持既有语义。
5. Trace 继续记录输入、校验和选择计数，并增加补充候选/发布计数。管理员查看空 Brief 时必须能直接读到一条中文漏斗说明。
6. 采集和调度失败沿用现有 `notifyFailure`、源健康熔断/半开恢复、后台源健康卡片；本次不复制第二套告警通道。

## 验收标准

- 当存在近期候选、但唯一可发布洞察只引用较早证据且其 `event_id` 未出现在发布基线时，Brief 发布该洞察并标记 `〔补充发现〕`。
- 相同条件下，若该 event 已在基线中出现，不能作为补充发现重新发布；若无 `event_id`，同样不能作为补充发现发布。
- 补充发现最多两条；主通道的近期洞察不受这个上限影响。
- 所有补充发现仍只渲染 `pass/support` 引用；blocked、flagged、未校验引用不进入报告。
- `generate_report.completed` 记录 `supplemental_candidate_count`、`supplemental_published_insight_count`，管理员 trace API 只投影登记的非负整数计数。
- 空 Brief 的溯源面板显示“分析 → 可纳入 → 新鲜度主通道过滤 → 已发布去重 → 补充发现 → 最终发布”漏斗及稳定原因码。
- 覆盖 report-gen 纯函数测试、`runReportGen → SQLite → generation_event` 集成测试、provenance 读模型测试和 `npm run typecheck`；本变更不跑 A1，因为 A1 不执行确定性报告选择路径。
