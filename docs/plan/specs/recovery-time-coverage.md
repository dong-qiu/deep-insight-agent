# C1：恢复时间与删除登记覆盖契约

状态：Proposed；实现与同镜像验收未完成。此文修正既有恢复设计冲突，不授权生产恢复或云资源变更。

## 1. 安全目标与时间

恢复旧备份不能恢复在快照之后已删除的内容。备份版本继续按现有规则保留，不要求所有版本在 90 天内删除。

- `snapshot_time`：备份可信 manifest 中数据库一致性采样的 UTC 时间/对应登记提交序号，绑定备份身份/摘要；不是文件打包完成时间，也不是删除筛选截止时间。多组件备份必须绑定最早相关采样边界；无法证明采样边界时拒绝。
- `replay_cutoff`：在删除写入方停止且受到隔离后，外部可信登记册检查点冻结的 UTC 时间；绑定检查点和本次恢复。
- `coverage_from`：检查点能证明完整覆盖的最早时间。备份早于此时间拒绝恢复，不自动删除该备份；仅满足这个时间不等式仍不足以放行，必须同时证明覆盖起点前的删除已包含于可信基线。
- runner 使用严格 UTC、解析后 ISO 毫秒形式和数值时间比较；拒绝日历无效、重复/未知参数、未来截止时间及 `snapshot_time > replay_cutoff`。
- 旧 `--restore-time` 含义不明确，升级后必须拒绝该单参数命令；不能悄悄改成“当前时间”。生产调用方、镜像脚本及文档必须一并迁移。

回放适用集合为登记册中 `effective_at <= replay_cutoff` 的已生效删除，**不以 snapshot_time 排除后续删除，也不以 expiry_at 静默排除旧删除**。所有检查点记录先做结构/时间/解密/HMAC 核验，再应用集合；未来记录或错误记录不能绕过核验后被静默跳过。

`expiry_at` 是既有登记记录的有限保留信息，不是“用户希望已删除内容重新出现”的授权。当前 resolver 仍使用 expiry 判定、报告读模型也有独立撤下动作，因此只改 runner 筛选不够；须设计恢复使用的持久删除约束，在 resolver 与报告/索引读模型一致生效。不能篡改已签名 expiry、伪造 registry 签名、把 expiry 随意延长到 2099 年，或用一个新时间字段绕过读者门。

## 2. 覆盖证明，而非人工填写日期

缺少完整性证明的恢复一律拒绝。`coverage_from` 不能来自用户填写的环境变量、扫描结果中的最早 effective_at、S3 列表成功或“记录数大于零”。空列表可能是确实没有删除，也可能是历史已清理，二者不能混同。

最小可信检查点要求：

1. 发布者独立于业务 SQLite/备份与应用写入角色；验证信任根由受控恢复环境提供，不从被恢复备份读取。不能让备份自签完整性声明。
2. 检查点包括版本、身份、登记册/epoch 身份、UTC coverage_from/cutoff、连续提交序号、所有登记记录的 immutable object key/version/字节摘要清单、清单摘要和可信签名。检查点可复用；恢复收据再绑定备份摘要、检查点摘要、运行镜像与结果，不要求发行者为每份备份重签。不同 bucket/prefix/epoch/清单的声明不得混用。
3. 发布者必须通过从 coverage_from 起的连续、不可变写入索引及保留证据证明“没有漏项”，不是对当前 ListObjects 的结果签名；还需绑定 coverage_from 之前已生效删除的可信基线状态（或自系统创始以来全量删除覆盖）。若没有该基线/索引或历史保留无法证明，不补造旧历史证明，旧快照保持不可恢复。不能用“快照在覆盖窗口内”推断它包含更早的全部删除约束。
4. 在所有删除写入入口被隔离后冻结检查点；恢复期间不得重新开放删除入口。原型首切使用共享维护闸门，保持关闭、经人工受控重新开放，不实现自动租约续期。闸门必须约束每个入口的实际提交，不只是请求接收。仅停止三个 compose 服务不证明其他 CLI/管理员写入口已停。每个成功外部登记（包括本地事务失败的孤儿）进入连续索引；检查点包含外部已提交但本地 pending 的记录。冻结屏障先排空在途请求，禁止冻结期间 pending 重试提交；索引缺口/待决写入/延迟重试无法排除时拒绝发行检查点。应用时钟的旧 effective_at 不能代替提交序号。
5. 先验证签名、备份与 epoch 绑定、采样边界/提交序号在覆盖内、coverage_from <= snapshot_time <= cutoff、截止时间不在未来，再核对实际对象 version/摘要、完整集合与分页。缺项/多项/版本不匹配/无法读取均拒绝，不用“跳过坏记录”补足计数。
6. 所需加密与 HMAC key version 必须仍可读取；登记对象和密钥的保留覆盖应与允许恢复的备份窗口一致。若外部清理或密钥销毁导致覆盖证明失效，拒绝相关备份；不因此删除或延长生产备份/云保留策略。

本契约先定义要求，不声称现有 S3 有检查点、连续索引或共享闸门。新增发行/验签协议、持久删除约束和迁移另按 spec/ADR 评审；在它们实现前，禁止将恢复成功事件当作生产启动证明。合成 fixture 的签名/transport 测试不能证明真实 IAM、Object Lock 或历史覆盖。

## 3. 事务、启动与失败

- 不触碰 live DB；先验证独立合成/恢复副本的备份完整性、身份与检查点。旧格式或缺失可信时间/身份的备份拒绝。
- 验证全部登记、解密与签名后，单一事务写持久删除约束并撤下受影响的报告、索引、FTS、复盘派生模型。一个坏记录导致整个回放失败。
- 幂等是相同备份/检查点重复执行结果不变，不是无条件接受冲突的同 record_id 新内容；必须拒绝冲突记录。
- 成功收据绑定备份、检查点、运行镜像、数据库结果与截止时间；记录数 0 只有可信空集合证明成立时可成功。日志不输出 entity key、secret、原文或个人身份。
- app/cron/worker 保持停止，直到回放、身份轮换、读者删除边界及同镜像 health/login/report 验收全部通过。旧收据不得启动被替换的数据库或镜像。
- 服务开放前再次核验维护闸门与截止检查点有效。若存在新删除、pending 提交或隔离失效，则重新冻结和回放，不放行旧 cutoff。生产 writer 必须走现有受控发布协议。

## 4. 实施顺序

1. 独立评审本契约，确认时间、长期备份覆盖、expiry 与 writer 隔离边界；不先改一行筛选就宣称安全。
2. 原型先建立全新的合成可信 epoch，只接受该 epoch 内、具有可信一致性采样边界的新格式备份；明确 epoch 前没有历史删除，不把它套用于已有生产数据。实现独立身份签名的连续索引检查点、共享维护闸门和独立于 expiry 的持久删除约束。首切只支持 report scope，出现任何其他 scope 则整次拒绝；不静默忽略。固定数据模型、迁移和调用方兼容策略。纯合成发行路径不使用真实云凭据；生产 epoch 启用需要完整基线与另行授权。
3. 迁移 runner 时间参数与全部调用方，补实际生产等价路径回归；未知覆盖始终拒绝。旧 reader/旧镜像禁止读恢复副本。
4. 同镜像 Node 24 验证合成新格式备份、成功回放、HTTP 删除不可见、AUTH_SECRET 轮换拒绝旧 cookie、新登录成功及服务启动编排。
5. 独立审查、PR/CI、脱敏收据；另行授权实际生产部署/恢复。TD-09 的合成恢复证据与真实登记册/IAM/历史数据恢复证据分开记录。

## 5. 必须落为可执行测试的矩阵

| 场景 | 目标断言 |
| --- | --- |
| 快照早于删除、删除早于 cutoff | 删除必须落库，所有对应 reader 不可见 |
| 快照晚于删除/相同时间 | 幂等回放，不重复 tombstone/派生副作用 |
| effective_at 等于 cutoff | 包含；以数值 UTC 比较，不因秒/毫秒格式漏项 |
| cutoff 之后的已签名记录 | 校验后拒绝陈旧检查点，不跳过放行 |
| 日历无效/非 UTC/未来/倒置/旧参数 | 非零退出，不产生可启动收据 |
| 过期删除但旧快照仍在覆盖内 | 持久删除仍有效，不重现实体；不修改原签名 |
| 快照早于 coverage_from/证明缺失 | 拒绝；保留原备份 |
| DB 在覆盖前采样、文件在覆盖后完成打包 | 拒绝，使用采样边界而非完成时间 |
| 时间在覆盖内但起点前删除基线未知 | 拒绝，不用时间不等式代替完整基线 |
| 可信空清单 vs 无证明空列表 | 前者可回放 0 条，后者必须拒绝 |
| 错误签名/备份绑定/信任根来自备份 | 拒绝，不写删除约束或启动服务 |
| 缺项/多项/错误版本/摘要/分页不完整 | 拒绝，不部分落库 |
| 缺 HMAC 或 KMS 版本/传输失败 | 拒绝，错误不含 secret/实体原文 |
| 混合正确记录与坏签名 | 删除写入全部回滚，不输出成功事件 |
| 同 ID 冲突内容、再次恢复或重复回放 | 冲突拒绝；合法重复结果不变 |
| 维护闸门失效/恢复中新增删除 | 禁止启动，重新冻结并回放 |
| 外部已提交、本地 pending；跨冻结在途登记 | 前者包含且可回放；后者未排空时拒绝冻结 |
| 冻结前 pending、冻结后延迟重试 | 提交闸门拒绝，不能用旧 effective_at 绕过屏障 |
| 首切出现非 report scope | 整批拒绝，不丢弃记录后宣称成功 |
| 旧数据库/镜像/过期收据替换 | 启动门拒绝旧收据 |
| AUTH_SECRET 轮换 | 旧 cookie 拒绝，新登录及允许报告正常 |

以上为待实现测试，不是已通过测试；现有 KNOWN GAP 现状断言将被第一行安全回归替换。生产历史缺口不因合成测试通过而消失。
