# Daily Brief 使用反馈：时效、覆盖与解读的有界诊断

> 2026-10-05（北京时间）· 只读探索诊断，不是新功能验收，也不改变现有发布门。

用户反馈：① 消息通常比期望晚约两天或更久；② 每期条数偏少，每条多为一句事实、缺少背景；③ 论文和播客缺核心观点与深入解读。本记录将三项分别定位，避免以消息变长或增加引用数替代验收。

## 机制诊断

1. **时效**：出刊前采集，但正式日报仅每日 17:00 UTC 一次；输入回看默认 7 天。选择器在存在近 48 小时候选时为它们保留至少 40% 的输入名额，余下仍按相关性和来源多样性填充。报告发布门要求近期候选的合格主引用，另允许最多两条明确标注的较早“补充发现”。因此“48 小时内”是允许上界而非时效目标；源发布时间、源进入库、入选分析、通过证据门和出刊分别可能产生延迟。当前副本的 `fetched_at` 可因同 URL 更新而改变，不能仅用它准确归因首次采集延迟。应使用冻结的采集/选择/发布 Trace 分段测量。
2. **条数与事件覆盖**：候选池默认最多 800 条，但每主题只取最多 15 条进入分析；来源形态与文章长度又限制模型可见内容。模型被要求只输出重要性至少 3 的事实；展示审计、validator、新鲜度、14 天历史检查和同批事件折叠依次减少可刊成员。S0 10 月 3 日软件工程首轮固定运行有 15 个输入 revision、47 条候选，仅 4 条成为已刊事实，且分属四个真实事件。这个样本不能推出另外两主题的损失比例。将同事件 2–3 个事实合成一条可提高**每条信息量**，但消息条数可能减少，所以必须同时测量独立重要事件数与重要维度覆盖。
3. **“不够新”的语义问题**：现行历史门主要按模型给的 `event_id`、严格原句指纹和已刊 `content_item_id` 判断；同一事实换来源或改写可能再刊，同一来源内真实新增的重要事实也可能被视为旧证据。该机制不能等同于“读者尚未见过的命题”。S0 首轮再次刊出既有 GPT-6.1 Sol 定价，支持将命题级新颖性单列为诊断和验收维度；不能只调短时间窗。
4. **一句事实、少解读**：现行 analyzer 要求一条 `Insight` 只表达一个实质命题，绑定唯一主引用；报告生成器逐条确定性渲染，不再生成分析段。自由 headline/重要性说明被收紧为受控字段，现有“系统重要性判断”只给工程选型、安全审查等通用类别，不表达论文机制、实验边界或播客嘉宾论证。即使模型产出多个互补候选，日报同批按事件 ID 只留一个代表项，也不合并其余引用。单纯放宽字数、增加引用或更换模型，不能保证出现核心观点。
5. **来源形态**：arXiv 适配器当前保存 API 摘要，不自动读取论文全文；普通非转写长文默认只把前 1 万字符给 analyzer。RSS 若正文已有摘要，`feed` 模式不会因其短而自动抓全文；`full_text` 按源配置执行。独立播客 RSS 可以只形成 `show_notes`；生产 collector 目前不调用 `fetchTranscript()` 从转写 URL 取全文，尽管部分 newsletter/feed 正文本身可能含转写。样本 73 条展示主引用对应 69 个 `article`、4 个 `show_notes`、0 个 `transcript` 形态；`article` 可能内含访谈文字，所以这不能证明没有播客内容，只表明不可据此宣称已做播客转写深读。

## 优化顺序与验收建议

1. **先建立三个独立基线**：按主题统计来源发布时间→首次可见采集→分析入选→证据合格→出刊的分段时延，刊出时/次日上午的年龄分布；固定全部输入事件，计算关键新事件召回、已刊旧事实比例、候选阶段损失；按新闻、短讯、技术博客、论文摘要/全文、播客 show notes/转写分层人工标注核心论点、机制/结果、限定与阅读理解。未知或未认证环节保留 `unknown`。
2. **时效与覆盖先做低风险试验**：用冻结输入离线比较调度/选择策略，不直接把近期门从 48 改成 24 小时，因为这可能进一步压低条数；优先查源更新与候选入选损失，建立“新事实而非新 URL”的历史检查。必须报告每期重要新事件数、48 小时内有证据消息比例、整刊重要事件漏报、重报和空刊率，避免以新鲜度提升掩盖召回下降。
3. **信息完整性沿用现有 S0→S1 快路径**：同一真实新事件的 2–3 个独立合格事实可并列为一条消息，每个事实有自己的证据；真正只有一个重要事实的来源保留短讯。首轮显示证据审计/选段也是供给瓶颈，因此多事实机会不足时优先离线评估 C1 首次提取与自足 quote 选择，不能把未通过审计的草稿直接放入新刊。
4. **另设“解读深度”产品切片**：论文至少区分研究问题、机制、关键结果/比较基线、实验范围与局限；播客至少区分嘉宾核心主张、论据/例子、反方或不确定性、适用场景。读者正文将“原文作者/嘉宾观点”和“系统根据已证事实作出的分析”明确标识。前者要有逐项原文证据；后者若允许上线，须先修订当前中性叙述与原子展示契约，定义可审计的推理范围、必要前提、反例和独立人工评测，不得把推断伪装成来源原话。摘要或 show notes 缺材料时明确降低深度，不编造论文全文或谈话内容。

当前单主题加速切片只处理第 3 项的一部分，不能以它通过就宣称用户提出的三项体验问题全部解决。扩大首发范围前，应先用上述指标证明不会牺牲时效和重要事件覆盖；“解读”需要独立的产品与证据契约。
